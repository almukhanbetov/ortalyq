# Редактор кода в классе и сервер выполнения

Во вкладке «Код» виртуального класса преподаватель и ученик пишут программу вместе и запускают её. Результат видят оба.

Редактирование работает всегда. Для запуска нужен **отдельный изолированный сервер** с Judge0 CE. Пока он не подключён, кнопка «Запустить» неактивна и показывает «Сервис выполнения не настроен». Фиктивных результатов нет.

## 1. Как устроено

```
Браузер ─ WebSocket урока ─▶ backend ── журнал Yjs (code_docs) ──▶ PostgreSQL
   │                            │
   └─ POST /code/runs ─────────▶│ права участника, лимиты, частота, снимок кода
                                ▼  HTTPS + X-Auth-Token (только с IP сервера приложения)
                 ┌──────── отдельная VM исполнителя ─────────────────────────┐
                 │ Caddy (TLS, фильтр IP и путей) → Judge0 server → Redis →  │
                 │ workers → isolate: namespaces + cgroup на каждый запуск   │
                 └───────────────────────────────────────────────────────────┘
```

**Совместное редактирование:**
- Документ Yjs содержит тексты `code` и `stdin` и карту `meta` с языком.
- Сервер не разбирает Yjs. Он нумерует бинарные обновления, сохраняет журнал урока и рассылает обновления второму участнику.
- Обновления Yjs коммутативны и идемпотентны. Поэтому одновременные правки сливаются без потери текста, а повторная доставка безопасна.
- Чужие обновления применяются с отдельным origin и обратно не отправляются, бесконечного обмена нет.
- После переподключения клиент получает журнал и досылает правки, которых нет на сервере, в том числе сделанные без связи.
- Журнал периодически сжимается. Состояние хранится отдельно для каждого урока и восстанавливается после перезагрузки страницы.
- Ctrl+Z отменяет только собственные правки.

**Запуск:**
- Браузер отправляет снимок кода и входных данных на момент нажатия. Дальнейшие правки на этот запуск не влияют.
- Backend проверяет, что пользователь — участник урока, по тем же правилам, что и для класса. Посторонний получает 404 и по HTTP, и по WebSocket.
- Backend проверяет лимиты и частоту, затем передаёт снимок исполнителю.
- Результат и автор запуска рассылаются обоим участникам и сохраняются как «последний запуск».

**Backend не выполняет пользовательский код** — ни через exec, ни через eval, ни через shell. Он только передаёт текст по HTTP.

**В логи не попадают** исходный код, входные данные, вывод и ключ доступа. Пишутся только урок, id запуска, язык, статус и время.

В таблице `code_runs` хранятся хеш и размер кода, а не сам код. Вывод хранится: он нужен, чтобы показать результат после обновления страницы.

## 2. Почему отдельный сервер

Контейнеры Judge0 работают в режиме `privileged` — этого требует песочница isolate. Поэтому:
- граница безопасности здесь — isolate (namespaces и cgroups) внутри **выделенной VM**, а не Docker-контейнер;
- обычный контейнер, особенно privileged, достаточной защитой не является;
- побег из песочницы даёт root на этой машине.

В Judge0 ≤ 1.13.0 были именно такие побеги ([GHSA-h9g2-45c8-89cf](https://github.com/judge0/judge0/security/advisories/GHSA-h9g2-45c8-89cf), [GHSA-3xpw-36v7-2cmg](https://github.com/judge0/judge0/security/advisories/GHSA-3xpw-36v7-2cmg)), а также SSRF в собственную БД при включённой сети ([GHSA-q7vg-26pg-v5hr](https://github.com/judge0/judge0/security/advisories/GHSA-q7vg-26pg-v5hr)). Все три исправлены в **1.13.1**.

Поэтому исполнитель **нельзя** размещать на сервере приложения 194.31.55.106: там приложение, база, секреты и Kubernetes. На VM исполнителя не должно быть других сервисов, секретов и ключей доступа к другим системам.

## 3. Как обеспечиваются ограничения

Источники: [judge0.conf](https://github.com/judge0/judge0/blob/master/judge0.conf), [isolate_job.rb](https://github.com/judge0/judge0/blob/master/app/jobs/isolate_job.rb), [API Judge0 CE 1.13.1](https://ce.judge0.com), [руководство isolate](https://www.ucw.cz/isolate/isolate.1.html).

| Ограничение | Значение ORTALYQ | Механизм | Проверка `check-runner.py` |
|---|---|---|---|
| Сеть | запрещена | isolate запускается без `--share-net`, поэтому программа получает отдельный network namespace только с loopback. `ALLOW_ENABLE_NETWORK=false` отклоняет запросы с `enable_network=true`, backend всегда передаёт `false`. | подключение к интернету, к `kubernetes.default.svc` и к серверу приложения |
| Kubernetes API | недоступен | исполнитель вне кластера; сети в песочнице нет | то же |
| Секреты | не передаются | isolate передаёт программе только переменные, заданные через `-E`: `HOME`, `PATH`, `LANG*`, `JUDGE0_*`. Переменные worker (`POSTGRES_PASSWORD` и т. п.) не передаются. | список `os.environ` |
| Файловая система | только песочница | видны `/box`, `/tmp` и системные каталоги контейнера только для чтения (`/etc` с `noexec`). `judge0.conf` и каталоги хоста VM в песочницу не монтируются. | чтение `/judge0.conf`, `/root` и т. п. |
| CPU | 2 с (+0,5 с) | `-t`, `-x`; превышение — статус 5 «Time Limit Exceeded» | бесконечный цикл |
| Общее время | 5 с | `-w` (wall time) | то же |
| Память | 128 МБ на весь запуск | `--cg-mem`, cgroup: сумма процессов, потому что per-process лимиты запрещены | выделение 600 МБ |
| Процессы и потоки | 16 | `-p` | fork в цикле |
| Вывод | 64 КБ на файл | `-f` (`max_file_size`) задаёт `RLIMIT_FSIZE`. stdout и stderr перенаправлены в обычные файлы, поэтому превышение должно давать SIGXFSZ (статус 8). Это вывод из исходного кода Judge0 (в документации прямо не сказано), поэтому он проверяется. Backend дополнительно обрезает stdout и stderr до 64 КБ каждый. | вывод 10 МБ |
| Код и ввод | по 64 КБ | backend: 413 до обращения к исполнителю | интеграционный тест |
| Частота | 10 запусков в минуту на пользователя, 20 на урок; один активный запуск на урок; 4 одновременных на backend | backend | интеграционный тест |
| Доступ к API | только backend | Caddy пропускает только `ALLOWED_IP` и пути `/submissions`, `/languages`, `/config_info`, `/about`. Judge0 требует `X-Auth-Token` (`AUTHN_TOKEN`). Порт Judge0 2358 не публикуется. Ключ хранится только в Secret `ortalyq-code-runner`. | — |
| Таймауты | 30 с + wall | backend: срок ожидания результата, отмена кнопкой «Остановить», отмена при остановке сервера. Недоступность — статус «Сервис выполнения недоступен». | юнит-тесты адаптера |

Расхождение документации, которое нужно учитывать:
- официальная инструкция развёртывания Judge0 1.13.1 рекомендует Ubuntu 22.04 и параметр ядра `systemd.unified_cgroup_hierarchy=0` (cgroup v1);
- современный upstream isolate требует cgroup v2, а образ Judge0 использует собственный форк isolate;
- о cgroup v2 и Ubuntu 24.04 в документации Judge0 ничего не сказано.

Поэтому следуем официальной инструкции Judge0 (Ubuntu 22.04 + cgroup v1) и **обязательно** запускаем `check-runner.py`. Если cgroups не работают, проверки памяти и процессов это покажут.

Python в Judge0 CE 1.13.1 — **3.8.1** (`language_id` 71), версии новее в CE нет. Python 3.8 больше не получает обновлений. Изоляцию обеспечивает isolate, но новые возможности языка (например, `match`) недоступны. Фактический список — `GET /languages` вашего исполнителя.

## 4. Требования к VM исполнителя

- Отдельная VM вне кластера ORTALYQ: Ubuntu 22.04, от 2 vCPU и 4 ГБ RAM, диск от 30 ГБ (образы Judge0 большие).
- DNS-имя (например `runner.<ваш-домен>`) с A-записью на IP этой VM. Если у VM есть AAAA-запись, а у сервера приложения — IPv6, добавьте его IPv6 в `ALLOWED_IP` через пробел или уберите AAAA.
- Входящие соединения:
  - 22/tcp — только с адресов администратора;
  - 80/tcp и 443/tcp — для Caddy и выпуска сертификата. Запросы не с `ALLOWED_IP` получают 403.
- Никаких других сервисов, секретов, ключей SSH к другим серверам и kubeconfig.

Docker ставится **только на эту VM**. На сервер приложения Docker не устанавливается, containerd не заменяется.

## 5. Установка (на VM исполнителя)

```bash
# 1) Docker Engine по официальной инструкции docs.docker.com (только на этой VM)

# 2) cgroup v1 — как в официальной инструкции Judge0 1.13.1
sudo sed -i 's/^GRUB_CMDLINE_LINUX="\(.*\)"/GRUB_CMDLINE_LINUX="\1 systemd.unified_cgroup_hierarchy=0"/' /etc/default/grub
sudo update-grub && sudo reboot

# 3) Официальный релиз Judge0 v1.13.1 (содержит judge0.conf и docker-compose.yml)
wget https://github.com/judge0/judge0/releases/download/v1.13.1/judge0-v1.13.1.zip
unzip judge0-v1.13.1.zip && cd judge0-v1.13.1

# 4) Файлы ORTALYQ из репозитория: deploy/code-runner/{docker-compose.yml,Caddyfile,configure-judge0.sh,check-runner.py,.env.example}
#    скопируйте в этот каталог (docker-compose.yml заменяет официальный — отличия описаны в его заголовке)
./configure-judge0.sh judge0.conf          # лимиты, запрет сети, случайные пароли и AUTHN_TOKEN
cp .env.example .env && nano .env          # RUNNER_DOMAIN, ALLOWED_IP=194.31.55.106

# 5) Firewall
sudo ufw default deny incoming && sudo ufw allow from <IP-администратора> to any port 22 proto tcp
sudo ufw allow 80/tcp && sudo ufw allow 443/tcp && sudo ufw enable

# 6) Запуск в порядке официальной инструкции
docker compose up -d db redis && sleep 10 && docker compose up -d
docker compose ps
```

Docker публикует порты в обход ufw. Поэтому в `docker-compose.yml` опубликованы только 80 и 443 (Caddy), а порт Judge0 2358 не публикуется. Не добавляйте `ports:` сервисам `server`, `db` и `redis`.

Ключ для ORTALYQ — значение `AUTHN_TOKEN` в `judge0.conf`. Передавайте его по защищённому каналу, не в чатах и тикетах.

## 6. Проверка исполнителя

Запустите с сервера приложения: Caddy пускает только его IP. Скрипт только отправляет HTTPS-запросы и ничего не устанавливает.

```bash
python3 check-runner.py https://runner.<ваш-домен> 71      # ключ спросит скрыто
```

Все проверки должны пройти. Если не прошли проверки памяти, процессов или вывода, cgroups и лимиты не работают — **не подключайте** исполнитель к ORTALYQ.

## 7. Подключение ORTALYQ

**Kubernetes** (администратор на сервере приложения):

```bash
deploy/k8s/scripts/set-code-runner.sh
```

Скрипт:
- спросит адрес, ключ (ввод скрыт) и `language_id`;
- проверит доступность исполнителя;
- создаст Secret `ortalyq-code-runner`;
- перезапустит backend.

Отключить запуск: `set-code-runner.sh --remove`. Без этого Secret backend работает как раньше: Secret объявлен как `optional`.

**Локальный Docker Compose**: заполните в `.env` переменные `CODE_RUNNER_URL`, `CODE_RUNNER_TOKEN`, `CODE_RUNNER_PYTHON_ID` и выполните `docker compose up -d backend`.

Ограничения по времени и памяти задаются переменными `CODE_RUN_*` (см. `.env.example`). Они не могут превышать `MAX_*` в `judge0.conf`, иначе Judge0 отклонит запрос, и в классе будет «Ошибка сервиса выполнения».

## 8. Проверка преподавателем и учеником

1. Преподаватель и ученик одного урока входят в класс и открывают вкладку «Код». На телефоне: «Доска / код» → «Код».
2. Один пишет программу, второй видит текст сразу. Можно править одновременно — текст обоих сохраняется.
3. В поле «Входные данные» вводится по строке на каждый `input()`, например `Айгерим`. Программа:
   ```python
   name = input()
   print("Привет,", name)
   ```
4. «Запустить» → у обоих появляется «Выполняется…», затем «Завершено», вывод и строка «Запустил(а): …».
5. `print(` → «Ошибка выполнения» и `SyntaxError` в stderr. `while True: pass` → «Превышен лимит времени». `print("x" * 10_000_000)` → «Превышен лимит вывода».
6. Обновите страницу — код, входные данные и последний результат восстановятся.
7. Посторонний пользователь (например второй демо-ученик) не открывает класс и получает 404 на API кода.

Автоматически то же проверяет `e2e/code-editor.mjs` (см. README).

## 9. Обслуживание

- Следите за [security advisories Judge0](https://github.com/judge0/judge0/security/advisories) и обновляйте образы. Номер версии меняется в `docker-compose.yml`, после обновления повторите `check-runner.py`.
- Смена ключа:
  1. на VM: новый `AUTHN_TOKEN` в `judge0.conf`, затем `docker compose up -d`;
  2. затем `set-code-runner.sh` на сервере приложения.
- **C++ и JavaScript.** В интерфейсе показываются только языки, для которых задан `language_id`. Для включения:
  - узнайте id через `GET /languages`;
  - задайте `CODE_RUNNER_CPP_ID` и/или `CODE_RUNNER_JS_ID` (добавьте ключи в Secret и строки `env` в `deploy/k8s/base/backend.yaml`);
  - проверьте компиляцию, ошибку компиляции и лимиты на исполнителе.
