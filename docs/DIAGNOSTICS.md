# Диагностика расписания и занятий

Задача — вместо непонятного «Нет свободного времени» или пустого списка показать подтверждённую причину и предложить действие. Пользователь получает помощь прямо на своём устройстве, администратор — данные для разбора.

Отдельной логики времени нет. Диагностика использует те же правила, что и рабочий код:

| Что | Где правило |
|---|---|
| Списки «Предстоящие» и «История» | `lessonScopeCond`, общий для `/api/lessons` и диагностики |
| Вход в класс | `classProblem` и `joinWindow` — те же, что у `/join` и WebSocket |
| Свободное время | `freeIntervals`, `mergeSpans`, `subtractSpans`, `earliestStart` |

Время сравнивается по серверным часам в абсолютных моментах. Показывается в часовом поясе профиля.

## Пользователь

**Страница записи к преподавателю.** Вместо общего «Нет свободного времени» показываются подтверждённые причины. Их может быть несколько:
- нет будущих интервалов;
- интервалы есть только позже 3 недель — с датой ближайшего;
- время в N из M интервалов занято;
- самый длинный свободный промежуток — X мин;
- сегодняшнее время уже прошло.

Каждый интервал оценивается отдельно. Ошибка загрузки показывается как «Не удалось загрузить расписание» с кнопкой «Повторить». Собственные записи ученика к этому преподавателю видны всегда, даже если свободного времени нет. Сведения о чужих занятиях не передаются.

**Расписание преподавателя** разделено на «Доступность», «Занято» и «Свободно». Уроки вне текущих интервалов доступности помечаются: изменение доступности бронирования не отменяет.

**«Не вижу урок / Не могу войти».** Кнопка есть:
- в кабинете;
- в «Моих занятиях»;
- на странице преподавателя;
- при ошибке входа в класс.

Проверка выполняется в браузере пользователя:

| Что проверяется | Как |
|---|---|
| Сессия и роль | `/api/auth/me` |
| Собственные уроки | `POST /api/me/lesson-check` — только уроки, где пользователь участник |
| Загрузка «Предстоящих» и совпадение с проверкой | `/api/lessons` |
| Свободное время для новой записи | только на странице преподавателя |
| Серверное время и расхождение часов устройства | по ответам сервера |

Временная ошибка (нет сети, 5xx) повторяется один раз. Страница не перезагружается, бронирования не меняются.

Возможные результаты:
- урок найден → «Войти в класс» или «Открыть занятие»;
- «Вход откроется …»;
- «Урок завершился» → «Открыть историю»;
- «Урок отменён»;
- «Сессия истекла» → «Войти снова»;
- «Нет связи с сервером» или «Не удалось загрузить занятия» → «Повторить»;
- предупреждение о часах устройства. Доступ к уроку определяет сервер, а не часы устройства.

**«Отправить диагностику».** Перед отправкой пользователь видит ровно те данные, что будут сохранены:
- время проверки и версию приложения;
- страницу без параметров;
- свой ID и выбранный собственный урок;
- коды ответов и `X-Request-ID` запросов;
- расхождение часов;
- браузер.

Не отправляются пароли, токены, cookies, содержимое урока и тела запросов и ответов. Сервер дополнительно принимает только разрешённые поля и значения.

Пользователь получает номер обращения `D-XXXXXX`. Без связи с сервером пишется «Обращение не отправлено» — с кнопками «Повторить» и «Скопировать сводку».

## Администратор

**Страница «Модерация» → «Обращения».** Для каждого обращения видно:
- пользователь, время, версия frontend и backend, урок;
- данные браузера: каждый запрос с кодом, ошибкой, `X-Request-ID` и длительностью;
- оценка сервера или «Причина не установлена».

Рядом кнопка «Серверная диагностика урока». Статусы: «Новое», «В работе», «Решено». «Решено» ставится только с подтверждённой причиной — существование записи в БД решением не считается. Смена статуса пишется в журнал (`history`).

`X-Request-ID` есть в каждом ответе API и в журнале backend (`rid=…`). По нему администратор находит запрос пользователя в журнале.

**Диагностика занятия по ID** — на той же странице или из CLI, только чтение:

```bash
kubectl -n ortalyq exec deploy/backend -- server diagnose-lesson -id <UUID>          # текстом
kubectl -n ortalyq exec deploy/backend -- server diagnose-lesson -id <UUID> -json
```

Отчёт содержит:
- участников с ID, ролью аккаунта, замаскированным email и часовым поясом;
- время в UTC и в поясе каждого участника;
- статус, отмену, признак демо;
- включение урока в списки обоих участников с причиной;
- право входа.

Проверяются несоответствия:
- неверные роли и заблокированные аккаунты;
- пересечения и дубли;
- аккаунты с тем же отображаемым именем — показываются их ID; одинаковое имя не доказывает, что это один аккаунт;
- урок вне доступности;
- статус, не обновлённый после окончания.

Без `-record` CLI работает в транзакции только для чтения. С `-record` предупреждения фиксируются как обращение.

**Данные автоматически не меняются.** Нет удаления и отмены занятий, нет смены `student_id` по совпадению имени. Исправления выполняются отдельно, вручную и с подтверждением.

## Обращения

Таблица `diagnostic_reports` (миграции 0006, 0007). Обращение без дублей: повторная проверка с тем же отпечатком возвращает тот же номер и увеличивает счётчик `hits`. После «Решено» новое повторение создаёт новое обращение.

## Версия приложения

Frontend и backend сообщают SHA одного релиза:

| Где | Как задаётся |
|---|---|
| GitHub Actions (`images.yml`) | передаёт `APP_VERSION=${{ github.sha }}` в оба образа |
| backend | вшивается при сборке (`-ldflags -X …config.buildVersion`); проверка: `server version` |
| frontend | `NEXT_PUBLIC_APP_VERSION` встраивается в собранный код при `next build` |
| Локальная разработка | `dev` |
| Переопределение для backend | переменная окружения `APP_VERSION` |
